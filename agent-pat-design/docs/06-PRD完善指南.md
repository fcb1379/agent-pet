# AI 桌宠 PRD 完善指南

> 文档状态：Approved（工作方法基准）  
> 版本：v1.0  
> 最后更新：2026-08-03

## 1. 文档目的

本文档用于指导 AI 桌宠产品从框架基准逐步发展为可设计、可研发、可测试和可验收的完整 PRD。

完善顺序遵循：

> 先验证用户价值，再定义核心体验，最后约束技术实现。

产品定义以[产品框架基准](00-产品框架基准.md)为上游依据。硬件能力、软件技术栈和协议实现不能反向替代用户问题与产品目标。

## 2. 推荐文档体系

不建议把所有内容持续添加到一份大型 PRD。推荐按照以下层级拆分：

```text
00 产品框架基准
   ↓
10 产品主 PRD
   ↓
20 电脑桌宠 PRD
21 硬件摆件 PRD
22 双端联动 PRD
   ↓
30 AI 适配、角色系统、设备管理等功能 PRD
   ↓
40 联动协议、软件架构、固件架构等技术设计
```

各层职责：

| 文档 | 回答的问题 |
|---|---|
| 产品框架基准 | 产品是什么、核心原则是什么 |
| 产品主 PRD | 为谁解决什么问题、首版交付什么 |
| 端侧 PRD | 电脑端、硬件端分别提供什么体验 |
| 双端联动 PRD | 完整场景如何跨端连续运行 |
| 功能 PRD | 某个独立模块的规则、流程和验收是什么 |
| 技术设计 | 如何实现已经确认的产品需求 |

## 3. 第一步：确认产品假设

先用一页内容回答：

- 谁会使用产品？
- 用户在什么场景下使用？
- 当前存在什么可观察的痛点？
- 为什么屏幕桌宠和实体摆件需要同时存在？
- 用户为什么会持续使用，而不是短期尝鲜后闲置？
- 什么指标能够证明产品有效？

### 3.1 当前推荐假设

```text
目标用户：
经常使用一种或多种 AI 工具完成办公、创作、分析或开发任务的知识工作者。

核心问题：
用户需要频繁切回不同 AI 窗口，检查任务是否完成、是否需要输入或是否等待授权。

解决方案：
通过同一角色在屏幕和实体摆件上的连续表达，
让用户低成本感知任务进度，并通过实体互动快速处理注意力切换。

核心价值：
减少用户主动检查 AI 状态的次数，而不是增加新的消息提醒。
```

### 3.2 用户研究

建议完成 5～8 次目标用户访谈和工作流观察。不要只问“是否喜欢桌宠”，而应记录：

- 用户一天发起多少次 AI 任务；
- 单次任务通常持续多久；
- 用户多久切回 AI 窗口检查一次；
- 错过等待确认会浪费多少时间；
- 哪些提醒有帮助，哪些提醒造成打扰；
- 用户是否愿意长期摆放实体设备；
- 用户对常驻软件、AI 状态读取和麦克风的隐私态度。

### 3.3 阶段产出

- 《用户与问题定义》一页文档；
- 用户访谈提纲；
- 访谈记录与证据摘要；
- 产品假设成立、调整或否定的结论。

**出口条件：**能够用一句话明确目标用户、主要问题和产品价值，并有真实用户证据支持。

## 4. 第二步：冻结首版场景

首版不要同时覆盖所有 AI 工具、电脑状态和硬件互动。选择一个端到端主流程。

推荐首版场景：

> 开发者启动编程 Agent，离开任务窗口继续工作；桌宠持续表达运行状态，在 Agent 等待确认或完成时提醒用户，用户通过实体摆件唤出对应任务。

### 4.1 推荐用户旅程

| 阶段 | 用户行为 | 系统状态 | 屏幕桌宠 | 实体摆件 |
|---|---|---|---|---|
| 启动任务 | 提交编程任务 | `thinking` | 进入工作动画 | 呼吸灯或工作表情 |
| 工具运行 | 切换到其他窗口 | `tool_running` | 保持低干扰 | 节奏变化 |
| 等待确认 | 用户未看 AI 窗口 | `waiting_user` | 显示简短气泡 | 明确提醒 |
| 实体互动 | 按键或拿起 | 互动事件 `picked_up` 或 `button_pressed` | 打开焦点会话 | 本地回应 |
| 用户确认 | 查看上下文并批准 | `tool_running` | 恢复工作动画 | 恢复执行表现 |
| 任务完成 | 查看结果 | `success` | 提供结果入口 | 短暂庆祝 |

### 4.2 需要补齐的场景细节

- 用户如何知道提醒对应哪个 AI 任务；
- 同时存在多个任务时如何选择；
- 勿扰模式下等待确认如何表达；
- 用户没有处理提醒时是否重复以及重复频率；
- 电脑锁屏、休眠、断连或 AI 工具退出时如何降级；
- 硬件动作如何唤出正确窗口；
- 任务成功后结果入口保留多久。

**出口条件：**团队能够完整演示一个闭环，不需要依赖“未来还可以增加”的能力解释核心价值。

## 5. 第三步：确定版本范围

建立三张明确清单。每个需求只能处于一个集合中。

### 5.1 MVP 必须有

- 一个真实 AI 工具适配器；
- AI 七类活动状态，以及独立的设备连接、用户模式和互动瞬态状态域；
- Windows 屏幕桌宠；
- BLE 连接、配对和重连；
- 实体状态表达；
- 至少一个实体输入；
- 勿扰模式；
- 隐私和连接状态展示；
- 基础诊断和恢复路径。

### 5.2 后续版本

- 多 AI 工具和多任务管理；
- 马达、复杂语音能力和角色资源包高级功能；当前 MVP 已要求基础屏幕交互和用户资源包导入。
- 更多姿态和触摸互动；
- 日程与专注模式；
- 多种硬件形态；
- 第三方扩展。

### 5.3 明确不做

- 常开麦克风；
- 摄像头；
- 手机 App；
- 在硬件显示 AI 对话全文；
- 多用户和云同步；
- 通过摆件直接批准高风险操作。

### 5.4 需求准入问题

新增需求进入 MVP 前必须回答：

1. 它服务哪个核心用户问题？
2. 不做它，主流程是否无法成立？
3. 它能否在 MVP 时间内被完整验收？
4. 它增加哪些跨端、硬件、安全或维护成本？
5. 是否可以通过更简单的方案验证同一假设？

**出口条件：**每个候选功能都明确属于“现在做、以后做或不做”。

## 6. 第四步：定义状态与规则

桌宠产品的核心不是页面数量，而是状态模型。需要详细定义：

- AI 状态；
- 电脑状态；
- 角色状态；
- 设备状态；
- 用户模式；
- 状态进入和退出条件；
- 优先级与冲突处理；
- 超时、恢复和异常行为。

### 6.1 状态需求模板

| 项目 | 示例 |
|---|---|
| 状态名称 | `waiting_user` |
| 用户语义 | AI 需要用户输入、选择或授权 |
| 进入条件 | AI 工具明确发出等待用户事件 |
| 退出条件 | 用户处理、任务取消、任务失败或连接中断 |
| 优先级 | 80 |
| 屏幕表现 | 气泡、任务入口、间歇动画 |
| 硬件表现 | 可辨识且克制的灯光、表情或动作 |
| 首次提醒 | 状态进入后立即提醒 |
| 重复策略 | 按逐渐降低的频率重复，设定总次数上限 |
| 勿扰表现 | 不发声、不做大动作，保留低亮标记 |
| 无屏降级 | 使用灯光节奏表达 |
| 异常降级 | 来源丢失时进入 `unavailable` 或 `offline` |
| 验收方式 | 状态转换、计时和双端一致性测试 |

### 6.2 首批必须定义的状态域

```text
AI：idle / thinking / tool_running / waiting_user / success / error / unavailable
设备：disconnected / connecting / connected / degraded / updating
用户模式：normal / focus / do_not_disturb
互动瞬态：button_pressed / picked_up / put_down / flipped / shaken
```

每个状态域都要补齐权威方、进入、退出、优先级、双端表现、勿扰和异常降级。`offline` 不作为 AI 状态；设备断连使用 `disconnected`，AI 来源不可用使用 `unavailable`。

**出口条件：**任意两个状态冲突时，都能确定最终状态、双端表现以及被打断状态如何恢复。

## 7. 第五步：定义用户交互合同

不能只写“支持按键、触摸或摇晃”。每个交互都应写成完整链路：

```text
输入条件
→ 硬件本地即时反馈
→ 上报语义事件
→ 电脑端解释
→ 权限与上下文判断
→ 执行产品动作
→ 双端最终反馈
→ 失败或断连处理
```

### 7.1 示例：长按进入勿扰

```text
用户长按功能键 1.5 秒
→ 硬件在 50 ms 内开始按下反馈，达到长按阈值后播放渐暗反馈
→ 上报 interaction.button_long
→ 电脑判断当前绑定与权限有效
→ 电脑切换勿扰模式
→ 下发新的完整状态
→ 双端进入勿扰表现
→ 若处于断连状态，硬件进入本地临时勿扰并记录带版本的用户操作；重连时上报，由电脑按用户模式所有权规则合并并回发最终状态
```

### 7.2 每个交互必须定义

- 单击、双击和长按阈值；
- 输入有效条件；
- 是否依赖当前上下文；
- 本地反馈延迟；
- 是否允许用户配置；
- 去抖和误触保护；
- 断连时是否有效；
- 是否涉及权限、付款、文件删除或其他危险操作；
- 重复事件如何保证只执行一次。

**出口条件：**每个输入都能从用户动作追踪到最终结果，并覆盖失败、断连和重复事件。

## 8. 第六步：定义电脑端界面

电脑端分别建立三个界面 PRD。

### 8.1 桌宠窗口

服务日常状态感知与轻交互：

- 角色动画；
- 简短气泡；
- 拖动和点击穿透；
- 当前任务状态；
- 快速展开任务。

### 8.2 托盘与快速面板

服务高频控制：

- 勿扰模式；
- 显示或隐藏桌宠；
- 当前任务；
- 硬件连接状态；
- 暂停监控；
- 打开控制中心。

### 8.3 控制中心

服务低频复杂配置：

- AI 工具接入；
- 硬件配对和升级；
- 角色与动作资源；
- 互动映射；
- 权限与隐私；
- 诊断与日志；
- 后续插件管理。

### 8.4 页面需求模板

每个页面至少定义：

- 用户目标；
- 入口与退出方式；
- 信息层级；
- 主操作和次操作；
- 正常、空、加载、错误、断连状态；
- 权限反馈；
- 键盘、鼠标和辅助功能；
- 验收标准。

先完成信息架构和低保真流程，再进入高保真视觉。优先验证用户能否找到任务、处理提醒和理解设备状态。

**出口条件：**核心用户旅程中的每一步都有明确界面承接，且异常状态不依赖日志才能理解。

## 9. 第七步：定义硬件体验

硬件 PRD 应描述体验结果，而不是只列器件。

### 9.1 体验规格示例

```text
设备未连接时，用户仅观察硬件就能识别离线状态。
夜间和勿扰模式不会出现高亮突变。
关键状态不能只使用颜色区分。
勿扰模式不播放声音或大幅机械动作。
按键或姿态交互在 50 ms 内产生本地反馈。
设备断连后仍保留本地互动。
安全状态不能被普通角色动画覆盖。
```

### 9.2 从体验映射到硬件

先确定需要表达或感知的语义，再选择：

- 屏幕；
- RGB；
- 功能键；
- IMU；
- 环境光；
- 马达；
- 扬声器；
- 触摸；
- 存储和供电。

**出口条件：**每项硬件能力都对应明确用户价值和验收场景；删除某个非核心外设不会破坏系统架构。

## 10. 第八步：补充非功能需求

硬件联动产品必须覆盖：

- AI 状态到双端反馈延迟；
- 本地交互反馈延迟；
- 连接可用率；
- 配对和自动重连；
- 长时间稳定运行；
- PC CPU、内存和电量占用；
- 硬件功耗与温升；
- 固件升级和失败恢复；
- 日志脱敏；
- 权限和隐私；
- Windows 锁屏、休眠、蓝牙关闭和用户切换；
- 无屏幕、无 TF 卡、无马达时的降级行为。

需求必须量化。例如：

```text
不合格：系统应低延迟响应 AI 状态。

合格：从收到可信 AI 状态事件到屏幕桌宠和实体摆件开始反馈，
P95 小于 1 秒，单端失败不得阻塞另一端表达。
```

**出口条件：**所有影响稳定性、安全、隐私和长期使用体验的要求均具有数值目标或明确测试方法。

## 11. 第九步：建立验收体系

每条 P0 需求应具有唯一 ID、优先级、前置条件和可执行验收方法。

### 11.1 需求示例

```text
ID：REQ-LINK-001
优先级：P0

需求：
设备与已绑定电脑断连后，应自动尝试重连。

验收前置：
设备已完成安全绑定，电脑端服务正在运行。

验收步骤：
1. 关闭电脑蓝牙。
2. 等待 30 秒。
3. 重新打开蓝牙。

预期结果：
1. 设备在断连后进入明确离线状态。
2. 蓝牙恢复后 10 秒内自动恢复连接。
3. 用户无需重新配对。
4. 重连后硬件角色状态与电脑权威状态一致。
5. 断连期间缓存的旧互动事件不会重复执行。
```

### 11.2 测试分类

- 功能验收；
- 状态转换测试；
- 跨端一致性测试；
- 异常与恢复测试；
- 性能和长期稳定性测试；
- 隐私与权限测试；
- 用户理解度和打扰度测试。

**出口条件：**每条 P0 需求都能由不参与设计的人按照步骤判断通过或失败。

## 12. 第十步：持续迭代 PRD

PRD 不是一次写完的静态文档。每轮迭代采用：

```text
提出假设
→ 制作交互样片或技术原型
→ 用户或实机验证
→ 记录结果
→ 修改范围和需求
→ 冻结本轮版本
```

### 12.1 变更记录必须包含

- 修改内容；
- 修改原因；
- 用户证据、技术数据或测试结果；
- 影响的电脑端、硬件端、协议和测试；
- 工期、成本、隐私和安全影响；
- 被替代或废弃的旧结论；
- 决策人和日期。

### 12.2 需求状态

建议每条需求使用以下状态：

```text
Draft       草拟中
Validated   已验证价值或必要性
Approved    已批准进入版本
In Progress 研发中
Verified    已通过验收
Deferred    延后
Rejected    明确不做
```

## 13. 推荐执行顺序

| 顺序 | 工作项 | 主要产出 | 出口条件 |
|---|---|---|---|
| 1 | 用户与问题定义 | 一页问题定义、访谈结果 | 核心问题有证据支持 |
| 2 | 首版用户旅程 | 主流程和异常分支 | 端到端价值闭环成立 |
| 3 | MVP 范围 | 做/后做/不做清单 | 功能边界清楚 |
| 4 | 状态系统 | 四域状态表、优先级和转换 | 冲突结果可确定 |
| 5 | 交互合同 | 按键、拿起等跨端链路 | 异常和权限完整 |
| 6 | 电脑端 PRD | 三类界面和状态 | 核心流程有界面承接 |
| 7 | 硬件 PRD | 体验规格和能力映射 | 外设均有用户价值 |
| 8 | 非功能需求 | 性能、安全、隐私和恢复 | 目标可测量 |
| 9 | 验收体系 | 需求 ID 和测试用例 | P0 可独立验收 |
| 10 | 技术设计 | 架构、协议和开发计划 | 需求到实现可追踪 |

## 14. 当前立即执行的三项工作

### 14.1 《用户与问题定义》

围绕通用知识工作者开展研究，并覆盖编程 Agent、内容创作和办公 AI 等子场景，记录检查 AI 状态的频率、等待损失和提醒偏好。

### 14.2 《核心用户旅程》

详细描述从 AI 开始运行、等待用户、用户通过摆件响应，到任务完成的主流程和异常分支。

### 14.3 《核心状态规格》

为以下四个正交状态域建立完整状态表：

```text
AI 活动状态
设备连接状态
用户模式
互动瞬态
```

每个状态补齐进入条件、退出条件、优先级、屏幕表现、硬件表现、提醒策略、勿扰表现、异常降级和验收方法。

完成以上三项后，再开始详细页面设计和硬件动作设计。否则容易得到视觉丰富但无法证明用户价值的产品。

## 15. PRD 完整性检查表

在宣布某一版本 PRD 可以进入研发前，检查：
